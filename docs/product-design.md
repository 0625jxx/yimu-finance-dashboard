## 1. 文档目的

本文档定义“个人财务管理与可视化看板”的整体产品方向、目标用户、核心体验、课程版本功能边界和关键数据口径。它是交互设计、技术设计、研发任务与测试用例的共同依据。

当前仓库已完成响应式 Web 课程提交版。本文仍作为产品基线，并把后续产品化需要研究或业务确认的内容集中列在“待确认事项”中，避免将设想误写成已实现事实。当前实现范围与架构决策见[技术设计文档](technical-design.md)。

## 2. 产品概述

### 2.1 一句话定位

为希望系统管理个人或家庭财务的用户，提供一个从记录、整理到分析和行动的一体化工具，让用户在几分钟内看清财务现状，并知道本月应该优先调整什么。

### 2.2 用户问题

用户的财务数据通常分散在银行卡、支付平台、现金和各类账单中。即使完成了记账，也经常无法快速回答以下问题：

- 当前实际拥有多少净资产，资产与负债分别如何变化？
- 本月钱主要花在哪里，哪些支出偏离了计划？
- 收入能否覆盖支出，未来一段时间是否有现金压力？
- 储蓄、还债或大额消费目标距离完成还有多远？
- 同一笔账是否被重复导入，账户余额与流水是否一致？

### 2.3 产品价值

产品不以“记录了多少笔账”为最终价值，而以“用户是否更快理解现状并采取调整行动”为结果。

核心价值链如下：

```text
采集财务数据 -> 自动整理与校验 -> 汇总关键指标 -> 发现异常或偏差 -> 给出可执行入口
```

### 2.4 产品原则

1. **先看全局，再看细节**：首页先回答资产、现金流、预算和目标四类问题，再允许用户下钻到具体流水。
2. **减少记录负担**：常用交易可快速录入，批量账单可通过模板导入，已有信息尽量复用。
3. **所有指标可解释**：图表中的金额可以追溯到原始交易；计算口径在界面中可查看。
4. **修改过程可控**：导入、批量分类和删除等高影响操作提供预览、结果反馈和必要的撤销能力。
5. **隐私默认开启**：只采集实现功能所需的数据；金额可隐藏；用户可随时导出或删除自己的全部数据。
6. **引导行动而非制造焦虑**：提醒应具体、克制，优先告诉用户发生了什么以及可以做什么。

## 3. 目标用户与场景

### 3.1 核心用户

**有稳定收入、拥有多个支付或金融账户，希望开始系统理财的个人用户。**

典型特征：

- 每月有工资或其他相对稳定的收入；
- 同时使用银行卡、微信、支付宝或现金；
- 愿意管理预算，但无法长期坚持复杂记账；
- 关心结余、储蓄和消费结构，不需要专业会计系统；
- 对个人财务数据的隐私和可迁移性较敏感。

### 3.2 次要用户

- 正在集中还债，希望跟踪负债下降速度的用户；
- 为旅行、教育或大额消费制定储蓄目标的用户；
- 需要合并观察家庭收入支出，但暂时可以由一个人统一维护数据的用户。

### 3.3 核心使用场景

| 场景 | 用户任务 | 期望结果 |
| --- | --- | --- |
| 每日快速记录 | 记录一笔支出、收入或转账 | 30 秒内完成，余额和分类同步更新 |
| 每周整理账目 | 导入账单，处理未分类和重复记录 | 快速完成清理，避免重复统计 |
| 月中预算检查 | 查看预算使用率和异常增长分类 | 找到超支风险并调整后续消费 |
| 月末复盘 | 对比本月与上月的收入、支出和结余 | 明确变化原因，形成下月预算 |
| 资产盘点 | 更新账户余额、资产和负债 | 获得可信的净资产快照与趋势 |
| 目标跟踪 | 查看储蓄或还债目标进度 | 知道剩余金额、预计完成时间和本期差额 |

## 4. 产品目标与边界

### 4.1 课程版本目标

- 让新用户在首次使用的 10 分钟内完成至少一个账户创建和一笔交易记录。
- 让已有账单的用户能够导入、检查并确认一批历史交易。
- 让用户在首页直接看到净资产、本月现金流、预算状态和目标进度。
- 让任意汇总金额能够下钻到构成它的交易，并能解释统计口径。
- 让用户拥有完整的数据导出与删除能力。

### 4.2 本次提交不做

- 银行或支付平台的实时自动同步；
- 股票、基金、加密资产的实时行情与交易；
- 自动报税、会计凭证或企业财务管理；
- 个性化投资推荐、贷款推荐或具有承诺性质的财务建议；
- 多人实时协作、复杂家庭权限与审批；
- 多币种汇兑损益核算。

这些能力不是永久排除，而是在验证基础记账、预算和看板闭环之前不进入首个可用版本。

## 5. 核心体验闭环

### 5.1 首次使用

```text
进入产品
  -> 选择默认币种和月度周期
  -> 创建现金/银行卡等账户
  -> 录入第一笔交易或导入账单
  -> 确认分类与余额
  -> 查看生成后的首页看板
```

首次流程必须允许跳过非必要配置。用户可以先看到结果，再逐步补充预算和目标。

### 5.2 日常使用

```text
快速记账/导入账单
  -> 系统更新账户与指标
  -> 首页暴露异常、超支或待处理事项
  -> 用户下钻核对
  -> 修改分类、预算或目标计划
```

### 5.3 月度复盘

```text
查看本月总结
  -> 对比上月和预算
  -> 定位变化最大的分类
  -> 检查异常交易与未分类交易
  -> 复制或调整下月预算
```

## 6. 信息架构

一级导航建议保持在七项以内：

| 一级模块 | 主要内容 | 用户首要问题 |
| --- | --- | --- |
| 首页 | 净资产、现金流、预算、目标、待办提醒 | 我现在的财务状态怎么样？ |
| 交易 | 流水列表、搜索筛选、批量分类、导入 | 每一笔钱去了哪里？ |
| 账户 | 资产账户、负债账户、余额调整、归档 | 钱和债分别在哪里？ |
| 预算 | 分类预算、总预算、使用进度、结转设置 | 本月还能花多少？ |
| 目标 | 储蓄目标、还债目标、进度和计划 | 距离目标还有多远？ |
| 报表 | 趋势、结构、对比和明细下钻 | 财务状况如何变化？ |
| 设置 | 分类、标签、导入规则、隐私、导出与删除 | 如何管理规则和数据？ |

移动端可将“新增交易”作为全局主操作，不占用一级导航位置。

## 7. 主要功能设计

### 7.1 首页看板

首页是产品的决策入口，不是所有图表的集合。首屏优先展示以下内容：

1. **净资产卡片**：当前净资产、与上月末差值、资产和负债构成。
2. **本月现金流卡片**：收入、支出、净现金流，以及与上月同期对比。
3. **预算进度**：总预算使用率、即将超支和已经超支的分类。
4. **目标进度**：最优先目标的完成比例、本期计划金额和差额。
5. **待处理事项**：未分类交易、导入冲突、长期未更新账户等。
6. **支出结构**：本月支出分类排行及占比，可点击下钻到交易列表。

交互要求：

- 支持按月切换，默认显示当前自然月；
- 所有金额卡片支持隐藏金额；
- 图表的空状态说明如何产生数据，而不是只显示“暂无数据”；
- 任何异常提醒都提供一个直接处理入口；
- 首页卡片使用同一统计周期，避免跨周期比较造成误解。

### 7.2 账户与资产负债管理

支持的基础账户类型：

- 现金账户；
- 银行卡或储蓄账户；
- 第三方支付账户；
- 信用卡或其他负债账户；
- 其他资产账户；
- 其他负债账户。

每个账户至少包含名称、类型、币种、期初余额、当前余额、是否计入净资产和状态。用户可以调整余额，但系统应把差额记录为一笔“余额调整”交易，以保持指标可追溯。

账户删除前必须提示其关联交易数量。存在交易的账户默认只能归档；彻底删除需要用户明确选择如何处理关联交易。

### 7.3 交易管理

交易类型包括收入、支出和转账。

单笔交易字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 类型 | 是 | 收入、支出或转账 |
| 金额 | 是 | 必须大于 0，由类型决定统计方向 |
| 发生时间 | 是 | 默认当前时间，可修改 |
| 账户 | 是 | 转账需要转出和转入账户 |
| 分类 | 收入/支出必填 | 可先进入“未分类”，但需在首页提示 |
| 商户/对方 | 否 | 用于搜索和后续规则匹配 |
| 标签 | 否 | 支持跨分类组织，例如“旅行” |
| 备注 | 否 | 用户补充说明 |
| 来源 | 系统生成 | 手动、导入或余额调整 |

关键规则：

- 转账不计入收入和支出，只改变两个账户的余额；
- 编辑或删除交易后，账户余额和所有关联报表同步重算；
- 支持按时间、账户、类型、分类、标签、金额范围和关键词筛选；
- 支持批量修改分类、标签和删除；批量删除需要二次确认；
- 重复交易提示不能直接阻止用户保存，用户可以确认其为不同交易。

### 7.4 分类与标签

- 提供一套可直接使用的收入和支出默认分类；
- 用户可以新增、重命名、排序和停用分类；
- 有历史交易的分类默认停用而非删除；
- 父子分类最多两级，避免层级过深增加记录成本；
- 标签用于跨分类主题，例如旅行、报销、家庭成员；
- 分类用于预算和主要报表，标签默认不参与预算汇总。

### 7.5 预算管理

课程版本使用月度分类预算，并保留后续扩展月度总预算的设计空间。

预算状态建议按以下规则展示：

- 正常：使用率低于 80%；
- 提醒：使用率达到 80% 且低于 100%；
- 超支：使用率达到或超过 100%。

功能要求：

- 创建、编辑、删除月度预算；
- 从上月复制预算到下月；
- 查看已用、剩余、使用率和日均可用金额；
- 点击某一分类直接查看计入预算的交易；
- 收入、转账、余额调整和已排除统计的交易不计入支出预算；
- 当前版本默认不自动结转未使用额度，后续可作为可选设置。

### 7.6 财务目标

课程版本支持两类目标：

1. **储蓄目标**：例如应急金、旅行、首付款；
2. **还债目标**：例如信用卡或其他负债的偿还计划。

目标字段包括名称、目标金额、当前金额、目标日期、关联账户、优先级和状态。用户可以手动更新进度，也可以关联账户余额计算进度。采用账户关联时，应明确展示计算来源，避免用户误以为系统自动识别了资金用途。

### 7.7 数据导入

课程版本支持 CSV；Excel 导入作为后续扩展项。导入采用上传、解析、重复检查和结果反馈流程：

```text
上传文件 -> 映射字段 -> 预览与处理冲突 -> 确认导入结果
```

功能要求：

- 允许映射日期、金额、收支方向、账户、分类、商户和备注；
- 在确认前展示成功、待补充、疑似重复和无法解析的数据量；
- 通过账户、金额、时间和商户等组合条件识别疑似重复记录；
- 用户可以逐条或批量决定跳过、覆盖或仍然导入；
- 一次导入形成独立批次，可查看结果并撤销整个批次；
- 原始文件不应无限期保留，保留策略需在隐私说明中明确。

### 7.8 报表与分析

产品规划中的完整报表包括：

- 净资产趋势；
- 收入、支出和净现金流趋势；
- 支出分类结构；
- 分类月度对比；
- 预算与实际支出对比；
- 目标进度趋势。

报表统一支持时间范围选择、账户筛选和明细下钻。饼图仅用于分类数量较少的构成场景；时间趋势优先使用折线图，分类比较优先使用条形图。

### 7.9 提醒与异常

课程版本仅提供站内提醒：

- 预算达到提醒阈值或超支；
- 存在未分类交易；
- 导入批次存在冲突；
- 目标进度落后于计划；
- 账户超过设定时间未更新。

提醒应支持标记已处理或暂时忽略。邮件、短信和推送通知放到后续版本，并由用户主动订阅。

### 7.10 数据管理与隐私

- 支持导出账户、交易、分类、预算和目标数据；
- 支持隐藏全部金额，适合公共场景查看；
- 敏感字段在传输和持久化时采用合适的加密措施；
- 登录、导出和删除等高风险操作保留必要的安全审计记录；
- 用户发起彻底删除前显示影响范围并再次确认；
- 删除完成后明确告知备份数据的清理周期；
- 不在未经明确授权的情况下将个人交易数据用于广告或第三方画像。

## 8. 关键指标与计算口径

所有指标默认基于用户所选时间范围、币种和“计入统计”的账户计算。

| 指标 | 计算口径 |
| --- | --- |
| 资产总额 | 所有计入净资产的资产账户当前余额之和 |
| 负债总额 | 所有计入净资产的负债账户当前未偿金额之和 |
| 净资产 | 资产总额 - 负债总额 |
| 收入 | 周期内收入交易金额之和，不含转账和余额调整 |
| 支出 | 周期内支出交易金额之和，不含转账和余额调整 |
| 净现金流 | 收入 - 支出 |
| 结余率 | 净现金流 / 收入；收入为 0 时显示为“不适用” |
| 预算使用率 | 计入预算的支出 / 预算金额；预算为 0 时显示为“未设置” |
| 目标完成率 | 当前金额 / 目标金额，展示值最高为 100%，超额另行提示 |

跨账户转账必须在统计层面抵消，否则会同时放大收入和支出。退款建议在课程版本中记录为对应支出的负向调整或关联退款交易，具体交互需在后续产品化阶段确认。

## 9. 核心数据对象

```text
用户 User
  ├─ 账户 Account
  │    └─ 交易 Transaction
  ├─ 分类 Category
  ├─ 标签 Tag
  ├─ 预算 Budget
  ├─ 财务目标 Goal
  ├─ 导入批次 ImportBatch
  └─ 提醒 Notification
```

核心关系：

- 一笔收入或支出交易属于一个账户和一个分类，可包含多个标签；
- 一笔转账关联一个转出账户和一个转入账户；
- 预算关联统计周期和一个分类，月度总预算可不关联分类；
- 目标可以关联一个账户，也可以由用户手动维护进度；
- 导入批次包含多笔交易，并记录映射、冲突处理和撤销状态。

数据模型需要保留创建时间、更新时间和必要的来源字段，以支持追溯、同步和故障排查。

## 10. 状态与异常体验

| 状态 | 设计要求 |
| --- | --- |
| 首次空状态 | 解释页面价值，并提供“新增账户”“记录交易”或“导入账单”入口 |
| 加载中 | 使用与内容结构一致的骨架屏，避免金额闪烁或布局跳动 |
| 局部失败 | 保留已经加载的内容，指出失败模块并提供重试 |
| 无筛选结果 | 展示当前筛选条件，并允许一键清除筛选 |
| 数据不一致 | 明确指出受影响账户或交易，提供核对入口，不静默修正 |
| 离线或网络异常 | 保存未提交输入或明确提示保存状态，避免用户重复录入 |
| 高影响操作 | 展示影响数量、结果和恢复方式；不可恢复时要求明确确认 |

## 11. 非功能要求

### 11.1 可用性

- 常用新增交易流程在正常情况下不超过 4 个必要输入动作；
- 桌面端和移动端均可完成核心任务；
- 金额、日期和图表颜色不能作为唯一的信息表达方式；
- 键盘操作、焦点状态、文字对比度和屏幕阅读器语义达到常见无障碍要求。

### 11.2 性能

- 常用页面在正常网络下应快速呈现首屏骨架和核心信息；
- 包含大量交易时，列表采用分页或虚拟滚动；
- 报表计算避免阻塞交易录入，必要时使用增量汇总或后台计算。

具体性能阈值需结合选定技术架构和部署环境确定。

### 11.3 可靠性

- 金额计算使用十进制或最小货币单位，禁止直接使用浮点数累计；
- 导入和批量操作具备幂等或重复提交保护；
- 指标更新失败不能导致原始交易丢失；
- 关键写操作应有事务边界和可定位的错误信息。

## 12. 课程提交版验收标准

满足以下条件才视为课程版本闭环成立：

1. 用户可以创建资产和负债账户，并正确看到净资产。
2. 用户可以新增、编辑和删除收入、支出、转账，账户余额同步正确。
3. 转账不计入收入和支出，余额调整可追溯。
4. 用户可以按常用条件查询交易并批量整理分类或标签。
5. 用户可以创建分类预算，看到已用、剩余和超支状态。
6. 首页的净资产、现金流、预算和目标金额均可下钻核对。
7. 用户可以完成一次 CSV 账单导入，处理字段映射和疑似重复记录。
8. 用户可以撤销尚在允许范围内的整个导入批次。
9. 用户可以导出个人数据，并能发起彻底删除。
10. 核心计算规则、异常场景和高影响操作均有自动化测试覆盖。

## 13. 成功指标

### 13.1 核心结果指标

建议将“月度财务复盘完成用户数”作为北极星指标。一次有效复盘至少包含：查看月度总结，并进一步查看预算、分类明细或目标中的任意一项。

### 13.2 过程指标

| 阶段 | 指标建议 |
| --- | --- |
| 激活 | 注册后 24 小时内创建账户并产生首笔交易的用户占比 |
| 数据建立 | 首周累计录入或导入至少 10 笔交易的用户占比 |
| 价值感知 | 首周查看看板后发生明细下钻的用户占比 |
| 习惯形成 | 连续 4 周至少每周使用一次的用户占比 |
| 行动转化 | 查看预算提醒后完成分类核对或预算调整的用户占比 |
| 数据质量 | 未分类交易占比、导入重复率、余额异常发生率 |

具体目标值应在取得首批真实用户基线后设定，不在产品初稿中虚构。

## 14. 版本规划

### 14.1 M0：可用原型

- 验证首页信息层级；
- 验证新增交易和导入流程；
- 验证用户是否理解净资产、现金流和预算口径；
- 使用可点击原型完成 5 至 8 名目标用户访谈。

### 14.2 M1：课程提交版（已完成）

- 账户、交易、分类与标签；
- CSV/Excel 账单导入和重复识别；
- 首页看板和基础报表；
- 月度预算和两类目标；
- 数据导出、删除和金额隐藏；
- 自动化测试、错误监控和基础安全控制。

### 14.3 M2：体验增强

- 记账模板、周期交易和更灵活的分类规则；
- 预算结转与年度预算；
- 自定义看板卡片和报表保存；
- 可配置的站外提醒；
- 多币种展示与基础汇率换算。

### 14.4 M3：协作与连接

- 家庭成员协作和权限；
- 经用户授权的金融账户同步；
- 更细致的资金预测与情景模拟；
- 开放的数据导入导出接口。

每个阶段均以前一阶段的使用数据和用户访谈为进入条件，不以功能数量作为唯一发布标准。

## 15. 风险与应对

| 风险 | 影响 | 应对方向 |
| --- | --- | --- |
| 记账负担过高 | 用户无法形成习惯 | 快速录入、批量导入、模板和规则逐步减负 |
| 数据不准确 | 用户不信任看板 | 可追溯口径、重复识别、余额核对和异常提示 |
| 首页信息过载 | 用户不知道看什么 | 固定核心四块，次要分析放入报表页 |
| 隐私担忧 | 用户拒绝录入真实数据 | 最小化采集、金额隐藏、清晰导出删除和安全说明 |
| 自动提醒引发焦虑 | 用户关闭提醒或流失 | 使用中性语言、限制频率、提供处理入口 |
| 功能范围快速膨胀 | 提交延期且难以验证 | 坚持单用户、手动/导入优先和基础闭环边界 |

## 16. 待确认事项

以下问题需要在原型评审或用户访谈中确认：

1. 首发形态是响应式 Web、桌面应用还是移动端优先？
2. 数据默认保存在本地、云端，还是提供两种模式？
3. 是否需要从第一版开始支持用户登录和跨设备同步？
4. 首批重点支持哪些账单来源及其文件格式？
5. 账户余额应完全由交易推导，还是允许用户输入余额并自动生成调整记录？
6. 退款采用负向支出还是独立退款类型，哪种更符合目标用户心智？
7. 首页卡片是否允许自定义排序，还是先使用固定信息层级？
8. 产品化版本是否需要支持数据加密密码或本地生物识别解锁？

这些问题不会阻止信息架构和低保真原型启动，但会影响技术架构与详细交互。

## 17. 下一步产物

建议按以下顺序继续：

1. 基于本文档制作首页、交易、导入、预算四条关键流程的低保真原型；
2. 用原型进行目标用户访谈，验证首页优先级和导入心智；
3. 形成页面清单、交互状态表和视觉设计规范；
4. 确认技术形态与数据存储方案，补充技术设计文档；
5. 将后续增强项拆分为用户故事、验收标准和端到端测试场景。
